either a raw export or is regenerated by a committed script. Only this README,
`mcp-connection-verified.txt`, `bedrock-cli-errors.txt` and `test-msg.json`
are hand-written. The first two quote real tool or terminal output.

## Final export, 29 Sep 2026 13:56:55 UTC

This is the last export for the build. Its numbers are copied from
`cloudtrail-timeline.md`, which the script generates.

- **1,554 events**, from 2026-09-28T18:45:22Z to 2026-09-29T13:49:42Z,
  under two IAM users: `MohitkPatwari@2005` 1,201, `secondbreath-dev` 353.
  By region: ap-south-1 1,258, us-east-1 296.
- **133 returned an error.** None is a failed deployment.
  - 105 are CloudFormation and SAM reading S3 bucket settings that were never
    set (`NoSuchCORSConfiguration`, `NoSuchLifecycleConfiguration` and five
    more kinds, 15 each), plus 1 `NoSuchBucketPolicy`.
  - 12 are `GetFunction` lookups before a function existed.
  - 3 are `LookupEvents` throttled during an export.
  - 2 are the Bedrock `Converse` attempts, refused with `ValidationException`.
    **This disagrees with the terminal.** `bedrock-cli-errors.txt` shows the
    Nova call refused with `AccessDeniedException` (account verification) and
    only the Claude Haiku call with `ValidationException`. CloudTrail logs both
    as `ValidationException`, "Operation not allowed", and records no model
    ID for either, so the events can't be matched to the commands. Recorded,
    not explained. CloudTrail corroborates that two calls were made and
    refused; the account-verification wording rests on the terminal capture
    alone.
  - 1 is `CreateDistributionWithTags` refused with `AccessDenied`: the
    CloudFront account-verification block.
  - The remaining 9 are lookups of things that did not exist yet, or bad
    parameters: `DescribeStacks` ×2, `DescribeLogGroups` ×2,
    `FilterLogEvents`, `GetOriginAccessControl`, `GetTopicAttributes`,
    `DescribeRule`, and `CreateServiceLinkedRole`
    ("AWSServiceRoleForAPIGateway has been taken": it already existed).

## How MCP calls look in CloudTrail, compared with plain CLI calls

The agent's MCP server signs as its own IAM user, `secondbreath-dev`, so its
calls can be separated **by principal**, not only by user agent.

| | Plain CLI (`aws ...` in a terminal) | Through the AWS MCP server |
|---|---|---|
| `userIdentity.arn` | `user/MohitkPatwari@2005` (or `secondbreath-dev` with `--profile agent`) | `user/secondbreath-dev` |
| `userIdentity.invokedBy` | absent | `aws-mcp.amazonaws.com` |
| `userAgent` | `aws-cli/2.x ... md/command#<service.op>` | `aws-mcp.amazonaws.com` |
| `sourceIPAddress` | the caller's IP (masked here) | `aws-mcp.amazonaws.com` |
| Region | the region the command names | the region passed to `call_boto3` (ap-south-1) |
| Extra event | none | an `AwsMcpEvent` in **us-east-1** from `aws-mcp.amazonaws.com` (`CallReadWriteTool`, `DestroySession`) whose userAgent is `python-httpx ... mcp-proxy-for-aws/1.7.0 claude-code/<version>` |

The timeline labels these `aws-mcp` (the account call) and `mcp-proxy` (the
MCP session event). Read-only MCP tools that never touch the account
(`list_regions`, `search_documentation`, `read_documentation`,
`retrieve_skill`, `get_regional_availability`) leave **no** CloudTrail
record. Only tools that act on the account show up. A plain
`aws ... --profile agent` call from a terminal is also `secondbreath-dev`,
but with an `aws-cli` user agent and no `invokedBy`, so it is not mistaken
for MCP.

## Limits, stated plainly

- CloudTrail Event history holds **management events only**. Data events
  (Lambda Invoke, S3 object reads) are not in it and are not claimed.
- Before the MCP user existed, the coding agent and the human shared one IAM
  user (`MohitkPatwari@2005`), so CloudTrail cannot tell them apart by
  principal. For those rows the *Caller* column uses `userAgent`: terminal
  calls (`aws-cli`, `sam-cli`, `Boto3`) came from the Claude Code sessions or
  the human typing in the same terminal, and `console` rows are the human in
  a browser.
- `secondbreath-dev` authenticates with `aws login` (a browser sign-in), so its
  `ConsoleLogin` / `CreateOAuth2Token` rows at the start of the MCP session
  are the human authorising the agent's profile, not the agent.
- Event history lags real time by up to ~15 minutes, and the export is a
  snapshot. Rerun the script at the end of the build.
- Calls made by the deployed Lambdas' own execution roles (for example
  `/health` reading SSM) are excluded by the principal filter.
